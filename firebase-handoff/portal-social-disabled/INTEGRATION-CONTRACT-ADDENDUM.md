# Draft auth-contract addendum — not deployed

Supersedes the native-provider-link implementation described in D-415 only after separate review/merge. Preserve historical contract text; integrate this as a new versioned decision in the owning repository, with its assigned decision number (do not invent or overwrite existing numbers).

- Native Google/Apple Firebase providers must be owner-confirmed disabled before canary; both blocking triggers remain None. Google Identity Services and standalone Apple OAuth remain configured independently.
- `socialIdentityLinks/{sha256(canonical issuer + NUL + subject)}` maps a verified external subject to true-case Auth UID and patient record ID. `socialIdentitySlots/{sha256(trueUid + NUL + provider)}` enforces one identity per provider slot. No Auth providerToLink, password/email changes or patient lookup by social email. Returning identities resolve by mapping first and recheck live Auth plus exactly one patient binding.
- First-time external identities retain the reviewed A/B resolver; mapping writes are transactionally collision-checked. Claim mapping and patient binding commit atomically under the same live lease. Cleanup never deletes a bound or password account.
- `socialAttempts` contains only nonce/proof digests, issuer-identity digest, authenticated actor UID, practice scope, expiry and stage. `socialAttemptThrottle` caps attempt creation at one per staff UID per 30 seconds. No bearer/provider/custom tokens or OTP values stored or logged. Bounded attempt is 10 minutes; completion is single-use. Lost completion response requires a NEW provider attempt; no retry returns or caches the previous custom token.
- `socialAvailability` returns only Google/Apple booleans. `socialBeginAttempt` and all A/B callables require live, enabled Auth plus an admin-owned `socialStaffTargets/{trueUid}` enabled target and master/practice switches. No email targeting; anonymous callers get no availability. This initial implementation is STAFF-ONLY and does not authorize member rollout. Target records are not user-writable; review/deny all new collection client access before deployment.
- All five callables explicitly use us-central1. Existing blocking functions and deployment workflow are untouched; do not use broad portal deployment while triggers must stay None. A future draft promotion needs a deployment path that excludes both blocking exports and cannot mutate trigger registrations.
- Runtime still needs Auth get/create/delete and custom-token signing; this proposal makes no IAM changes. Preflight reads remain identity-independent when the read-only account has viewer, as owner decided; no compute impersonation.
- Google frontend uses an explicitly public client setting matching SOCIAL_GOOGLE_CLIENT_IDS. The provided secret reference has not been exposed. Apple return URL must be separately authorized for its Services ID; never substitute Firebase handler.

Not yet verified: full owning-repository existing emulator suite, signed-token validation through full callable wrappers, hosted providers-disabled refusal/custom-token exchange, My Health Hub applied/released UI, Apple return authorization and real A/B/C read-back.
